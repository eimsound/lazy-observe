# 将 Ent 隔离在元数据持久化接缝（persistence seam）之后

告警引擎、采集目标和启动调用方当前直接使用公开的 Ent 客户端，并自行组合 schema 谓词、关联边加载（edge loading）、项目隔离和多步写入。我们决定把这些知识收回元数据实现：目标调用方只通过行为级接口表达所需结果，Ent、双方言差异和持久化顺序位于接缝（seam）之后；告警引擎仍拥有评估与通知语义，采集目标模块仍拥有校验、配置渲染和重载行为。

## 已考虑的方案

- **行为级元数据接口（采用）**：复用现有 SQLite/PostgreSQL 适配器与测试夹具（fixture），通过扩展、迁移、收缩逐步移除公开的 Ent 客户端。该选择提高代码局部性（locality），同时不会制造只有一个生产适配器的虚假接缝。
- **逐表仓储接口（per-table repository interface，拒绝）**：它会把 Ent 的增删改查机械映射为大量浅模块，导致接口贴近实现；测试替身会成为引入接缝的唯一理由。
- **一次性重构整个元数据模块（拒绝）**：它会把无关的账户、会话、审计、Issue、Replay、Profile、迁移和发件箱行为纳入同一变更，扩大风险，却不能提升当前调用方从抽象中获得的收益。

## 后果

- 目标模块不再导入 Ent 查询/schema 实现，也不获取生成的客户端；迁移完成后，Store 的 Ent 客户端成为私有实现。
- 告警规则相关的多步持久化结果必须原子提交，但不得把告警引擎的领域决策移动到元数据模块。
- 简单行为仍可由小方法实现，但不得重新暴露查询构造器（query builder）、生成的客户端，或要求调用方掌握写入顺序。
- 本决定不改变 ADR 0001 的告警引擎（Alert engine）语义，也不改变 ADR 0003 的 Ent 生成和元数据基线（Metadata baseline）策略。
