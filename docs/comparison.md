# Open-source self-hosted observability comparison: lazy-observe, SigNoz, OpenObserve, Sentry, and Traceway

This document helps engineering and operations teams compare lazy-observe with SigNoz, OpenObserve, Sentry (self-hosted), and Traceway across five dimensions: architecture trade-offs, deployment complexity, ecosystem compatibility, capabilities, and explicit boundaries.

> **Scope and methodology**
>
> - This comparison covers architecture facts and engineering trade-offs only. It omits synthetic benchmarks detached from hardware and workload conditions and avoids disparaging competing projects.
> - Every lazy-observe claim reflects the current `main` branch implementation, with links to relevant documents and ADRs. The project is in v0.x public preview. Check the [version compatibility matrix](version-matrix.md) for current compatibility details.
> - Competitor architecture details, capabilities, and licenses change across upstream releases. Verify details in each project's upstream repository and official documentation before selecting a platform.

## 1. Positioning and core differences

lazy-observe is built for small, medium, and larger self-hosted teams that want a single-binary starting point, a path to an HA cluster, direct compatibility with Prometheus and Victoria tooling, and four telemetry signals alongside frontend and backend diagnostics. It does not aim to be a hyperscale multi-tenant SaaS or an editable replacement for Grafana. Five verified implementation differences set its scope:

### 1.1 Single CGO-free binary (`CGO_ENABLED=0`) and zero-dependency all-in-one startup

- **Single-binary startup.** Releases ship as a static pure-Go binary (`CGO_ENABLED=0`, Linux `amd64` and `arm64`) that embeds the compiled web UI, a SHA-256 checksum manifest, and four pinned Victoria executables (`victoria-metrics-prod`, `victoria-logs-prod`, `victoria-traces-prod`, and `vmagent-prod`). Metadata defaults to pure-Go SQLite (`modernc.org/sqlite` in WAL mode), and local blobs write to `<data_dir>/blobs/`.
- **Single port and process supervision.** Evaluation and small-to-medium deployments do not need a multi-container stack of ClickHouse, Kafka, ZooKeeper, PostgreSQL, and Redis. By default, the gateway exposes only `:3100`, with optional native OTLP/gRPC ingestion on `:4317` when you set `otlp_grpc.enabled: true`. Managed child processes bind only to loopback addresses and run with independent exponential backoff restarts and two-phase graceful draining and shutdown.
- **Upgrade path to an HA cluster.** The same binary and `storage.SignalBackend` abstraction run in both standalone and clustered-HA modes. When a single host is no longer enough, you can switch to an external VictoriaMetrics cluster (`vmselect` and `vminsert`), split-role VictoriaLogs and VictoriaTraces, external PostgreSQL, Redis or Valkey (for shared sessions and rate limiting only), and S3-compatible object storage. The repository includes a Helm chart (with a three-replica cluster configuration), Docker Compose files, and systemd manifests. See [Deployment](deployment.md) and [Operations](operations.md).

### 1.2 Native Prometheus and MetricsQL compatibility with Grafana and Perses for dashboards

- **Victoria-only signal storage.** Under [ADR 0013](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0013-signal-storage-is-victoria-only.md), metrics, logs, and traces always use VictoriaMetrics, VictoriaLogs, and VictoriaTraces. Fixing the storage layer avoids cross-backend semantic loss and extra adapter maintenance.
- **Prometheus protocol compatibility.** Metrics ingestion supports OTLP/HTTP (`/v1/metrics`), optional native OTLP/gRPC (disabled by default via `otlp_grpc.enabled: false`; listens on `:4317` when enabled), Prometheus remote-write 1.0 (`/api/v1/write`), and active scraping of Prometheus exporters through built-in `vmagent`. Metrics queries run PromQL and MetricsQL through standard Prometheus endpoints (`/api/v1/query`, `/api/v1/query_range`, `/api/v1/series`, `/api/v1/labels`, and `/api/v1/label/:name/values`).
- **Fixed built-in views.** Under [ADR 0017](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0017-no-built-in-dashboards.md), lazy-observe ships fixed diagnostic workspaces (Overview, Application Performance, host list and details, LLM usage and cost, Metrics/Logs/Traces query workspaces, and Continuous Profiling). It deliberately omits a drag-and-drop dashboard editor and a built-in middleware template library. Connect Grafana or Perses when you need custom dashboards or want to reuse existing Grafana dashboards. Metrics endpoints connect out of the box, while logs and traces route through a lightweight path-rewriting proxy that forwards auth headers. See [Grafana and Perses integration](grafana-perses.md).

### 1.3 Storage-layer project isolation and least-privilege token boundaries

- **Gateway-enforced tenant isolation.** Storage ports stay private. Every read and write passes through the gateway, which validates and rewrites tenant boundaries:
  - **VictoriaMetrics.** On writes, the gateway overwrites the `project_id` label for OTLP, Web Vitals, and Prometheus remote-write 1.0, and decodes and rewrites protobuf labels. On reads, it strips client `extra_filters` and `extra_label` parameters and injects trusted filters.
  - **VictoriaLogs and VictoriaTraces.** On both reads and writes, the gateway removes and overwrites upstream `AccountID` and `ProjectID` tenant headers.
- **Strict separation across three token types.** See [ADR 0010](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0010-project-api-tokens-are-ingest-only.md) and [ADR 0018](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0018-source-map-upload-token.md):
  - **Project API token (`lo_`).** Embedded in SDK DSNs, including public browser pages, and restricted to telemetry ingestion. Any read route, including `/mcp` and `/api/system/info`, returns `403 ingest_only_token`.
  - **User API token (`lou_`).** Bound to the user's current RBAC role (`admin`, `member`, or `viewer`) and paired with the `X-LO-Project` header for Grafana, Perses, MCP, and CLI tools. It cannot ingest telemetry.
  - **Source Map upload token (`los_`).** Stored in a separate database table as a project-level CI secret for `POST /api/releases/:release/sourcemaps`. This keeps public browser `lo_` tokens from tampering with release Source Maps and avoids putting personal `lou_` tokens in CI pipelines. Any other route returns `403 upload_only_token`.

### 1.4 Single-leader leased alert engine, durable outbox, and built-in Chinese IM channels

- **Built-in evaluator.** Under [ADR 0001](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0001-nightingale-style-alert-engine.md) and [ADR 0011](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0011-sqlite-alert-lease-millisecond-clock.md), you do not need to deploy or operate `vmalert` or Alertmanager. The gateway process evaluates PromQL and MetricsQL rules, LogsQL threshold rules, and platform events such as new issues and regressions. In multi-replica HA deployments, Rendezvous consistent hashing and PostgreSQL rule leases with a monotonically increasing fencing epoch allow at most one valid committer per rule at a time. Lease expiration always reads the database clock, with millisecond clock handling on SQLite to avoid whole-second truncation.
- **Durable notification outbox.** Alert state transitions and notification enqueueing commit atomically in a single database transaction. Dispatch workers claim due tasks with database row locks (PostgreSQL `FOR UPDATE SKIP LOCKED`), handle expired-claim takeover, apply bounded exponential backoff retries, retain dead letters, and send HTTP `Idempotency-Key` headers for durable at-least-once delivery. Per channel, each alert's notifications are delivered in causal order: a firing notification still pending or retrying holds back the resolved notification behind it until it is delivered or dead-lettered. Alert state and queued notifications survive Redis failures and replica restarts.
- **Noise reduction and built-in IM channels.** The engine supports `group_wait`, `repeat_interval`, `storm_threshold`, silences, inhibition rules, and per-channel rate limits. Built-in channels cover Feishu/Lark (interactive cards), DingTalk (Markdown), WeCom (Markdown), Slack (Blocks), Webhook (JSON, custom headers, and `Idempotency-Key`), and SMTP/Email (STARTTLS and implicit TLS). The dispatcher checks business error codes returned inside HTTP 200 responses by Feishu, DingTalk, and WeCom (`code`, `StatusCode`, and `errcode`).

### 1.5 Four signals, error tracking, session replay, continuous profiling, and four SDKs

- **Built-in diagnostics.** Alongside OTLP/HTTP (`/v1/metrics`, `/v1/logs`, and `/v1/traces`), optional native OTLP/gRPC (disabled by default via `otlp_grpc.enabled: false`; listens on `:4317` for traces, metrics, and logs when enabled), and Prometheus remote-write 1.0, lazy-observe includes:
  - **Error tracking.** Receives error events through a durable metadata inbox so accepted events survive backpressure and restarts, and returns `503` explicitly when the inbox is full. Groups events into issues by stack fingerprint, detects regressions, and maps minified frontend frames back to source code with Source Maps.
  - **Browser RUM and session replay.** Collects LCP, CLS, INP, TTFB, and FCP Web Vitals, links `fetch` and `XHR` requests to backend traces, and records privacy-first DOM session replays that mask all input values by default and honor `[data-lo-block]` subtrees.
  - **Continuous profiling.** Aggregates pprof flame graphs for Go (CPU, heap, and goroutine), Node.js (V8 CPU and sampled-heap), and Python (experimental; Linux free-threaded CPython 3.15t or newer without the GIL for in-process CPU sampling, see [ADR 0014](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0014-python-profiling-on-cpython-315-sampling.md)).
  - **GenAI analytics (on by default) and read-only MCP.** Tracks LLM calls, token usage, and estimated cost from `gen_ai.*` spans in VictoriaTraces using a built-in model pricing table, without turning on AI under Settings or configuring an external LLM API key. `/mcp` and `lazy-observe mcp` expose project-isolated read-only MCP tools.
  - **Optional platform AI assistant (off by default).** Admins can configure a BYO LLM (OpenAI, Anthropic, DeepSeek, or native Ollama) under Settings, AI. It powers only natural-language MetricsQL/LogsQL generation and explanation and asynchronous cross-signal analysis for new issues.
- **Four explicit SDKs.** Maintained in the same repository: [Go SDK](sdk/go.md) (Fiber v3, `slog`, `database/sql`), [Node SDK](sdk/node.md) (Express, Pino, Winston), [Browser and React SDK](sdk/browser.md) (with `@lazy-observe/bundler-plugin` Vite plugin and CLI), and [Python SDK](sdk/python.md) (Django, DRF, `logging`, DB, and LLM instrumentation). None of them rely on invasive global monkey-patching, and all follow the shared degradation rules and [version compatibility matrix](version-matrix.md).

### Typical fit at a glance

- **Choose lazy-observe** when you want low-overhead self-hosted observability (single binary to start, external Victoria cluster plus PostgreSQL and S3 later), already use Prometheus, Grafana, or Perses, and value an MIT license, native Feishu, DingTalk, and WeCom alerts, and strict token separation across ingest, read, and Source Map upload.
- **Choose SigNoz** when your team has standardized on OpenTelemetry and wants a ClickHouse-backed backend APM and three-signal platform with built-in editable dashboards.
- **Choose OpenObserve** when log and metric volumes are high, you want S3 plus Parquet to minimize long-term storage cost, and AGPL-3.0 plus a built-in dashboard suite fit your requirements.
- **Choose Sentry (self-hosted)** when mature error tracking, native mobile SDKs (iOS, Android, Flutter), release health, and Cron monitoring are your top priorities and you have the capacity to run a heavy multi-container stack.
- **Choose Traceway** when you prefer MIT licensing and a Go plus ClickHouse architecture and want built-in dashboards or Flutter mobile session replay out of the box.

## 3. When not to choose lazy-observe

Do not choose lazy-observe right now if your team has any of these hard requirements:

1. **Multi-tenant commercial SaaS or petabyte-scale ClickHouse OLAP ad-hoc analytics.**
   - lazy-observe is built as a single-team self-hosted system that partitions data by project, not as a commercial SaaS control plane for external tenants. Deploy separate instances when unrelated organizations need hard isolation.
   - If your workload depends on massive columnar OLAP aggregations or custom ClickHouse SQL reporting, ClickHouse-based or object-storage lakehouse platforms such as SigNoz or OpenObserve fit better.

2. **In-product drag-and-drop dashboard editing without Grafana or Perses ([ADR 0017](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0017-no-built-in-dashboards.md)).**
   - lazy-observe ships fixed diagnostic pages only. It does not provide an editable dashboard engine or built-in host and middleware dashboard templates.
   - If you require every custom dashboard to be built inside a single UI with no external tools, pick a product with a built-in dashboard editor, or plan a Grafana or Perses deployment alongside lazy-observe.

3. **Native mobile SDKs (iOS, Android, or Flutter) or Cron monitoring.**
   - This repository ships four SDKs: Go (Fiber v3), Node.js (Express), Browser and React, and Python (Django and DRF). It has no native iOS, Android, or Flutter SDK and no dedicated Cron or heartbeat monitor.
   - Python continuous profiling is experimental and works only on Linux free-threaded CPython 3.15t or newer without the GIL because of CPython GIL sampling blind spots ([ADR 0014](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0014-python-profiling-on-cpython-315-sampling.md)). Native OTLP/gRPC (`:4317`) is disabled by default (`otlp_grpc.enabled: false`), requires explicit opt-in, and covers traces, metrics, and logs only; private signals (errors, vitals, replay, and profiles) still use HTTP.

4. **GA-grade in-place database upgrades across major versions or a commercial SLA ([ADR 0003](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0003-pre-release-single-database-baseline.md)).**
   - lazy-observe is in v0.x public preview and has not shipped its first supported GA release. SQLite and PostgreSQL each maintain a single mutable `001_baseline.sql` file, with no promise of in-place upgrade or downgrade migrations across incompatible schema changes. Upgrades may require rebuilding the metadata database (see [Operations](operations.md)), and protocol or SDK contracts may still break (see the [version compatibility matrix](version-matrix.md)).
   - This is an MIT-licensed community open-source project with no commercial SLA or round-the-clock support contract.

5. **Reusing existing non-Victoria signal stores such as Loki, Tempo, Jaeger, Mimir, or Thanos ([ADR 0013](https://github.com/eimsound/lazy-observe/blob/main/.agents/docs/adr/0013-signal-storage-is-victoria-only.md)).**
   - Metrics, logs, and traces storage is fixed to the Victoria stack (VictoriaMetrics, VictoriaLogs, and VictoriaTraces). Loki LogQL and Tempo TraceQL adapters are out of scope. `storage.metrics.kind: prometheus` remains in code but is neither officially supported nor release-verified.
   - Trace storage limits and release cadence are tied to upstream VictoriaTraces (currently v0.x) and cannot be swapped for Tempo or Jaeger.
