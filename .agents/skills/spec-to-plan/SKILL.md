# 从规格到计划

把已经确定的规格转换为可供另一个编码会话直接执行的持久化指令。只制定计划：不要修改生产代码、测试、
生成文件或配置。仅当用户指定保存位置时才持久化计划；否则以 Markdown 返回，供用户审阅。

## 用仓库事实约束计划

1. 完整阅读源规格，包括其中链接的决策和验收标准。
2. 阅读 `AGENTS.md`、`GLOSSARY.md`、相关 ADR 和架构文档，再检查当前实现、邻近测试和 `mise` 任务。
   全程使用项目的领域词汇。
3. 根据仓库逐项核实已有路径、符号、接口和命令。此前的对话只是上下文，不能证明当前目录树仍具有相同结构。
4. 优先从仓库证据中补齐缺口。只有某个未决选择会实质改变计划时才询问用户；较小的不确定性应记录为显式假设
   或调查步骤。

不要改写源规格，也不要悄悄增加产品行为。把规格中的需求映射到计划，并保留其范围外边界。

## 比较两条路线

确定设计前，先勾勒两条真正不同的实施路线。每条路线都要说明：

- 模块形态和公共接缝；
- 主要权衡与失败模式；
- 所需迁移或预重构（prefactoring）；
- 它为何符合或违背仓库当前的决策。

推荐其中一条路线。如果两条路线都可行，而规格尚未作出选择，应先让用户决策，再完成详细计划。如果仓库约束
只允许一条路线，仍需简要列出被否决的路线，并说明排除它的具体约束。

## 选择测试接缝

找出数量尽可能少、稳定且公开的行为接缝。优先使用现有接缝，并选择无需触及内部实现就能证明行为的最高层接缝。
复用附近已有的测试模式。

如果源规格已经批准测试接缝，直接沿用；否则先提出建议并获得确认，再完成计划。不要针对私有方法、内部调用次数
或其他实现细节制定测试。

## 使用 Tracer Bullet 切片

让每个实施步骤都成为一个 **Tracer Bullet（曳光弹）**：它以很窄的范围纵向穿过所有必要层，最终产生可观察、
可独立验证的行为。不要创建“先做全部数据模式（schema）”“再做全部处理器（handler）”“最后写全部测试”
这类横向阶段。

- 阻塞项排在依赖项之前，并显式写出每条阻塞关系。
- 每个切片应小到能在一个专注的编码上下文中完成，同时又足以交付一种真实行为。
- 如果现有结构使行为难以加入，先规划一个狭窄的预重构步骤：先让改动变容易，再完成这个容易的改动。
  预重构必须保持行为不变，并具备独立验证方式。
- 对无法通过纵向切片持续保持绿色的宽范围机械重构，采用扩展（expand）→ 迁移（migrate）→ 收缩（contract）。
  每个阶段结束后都保持工作树绿色；除非规格明确要求，否则不要引入旧版本兼容行为。

## 在每个切片中执行 TDD

每个 Tracer Bullet 都在已确认的接缝上测试先行：

1. **Red（红）**——先增加一个行为测试。写明预期失败及能够证明该失败的准确命令。断言必须来自规格或其他独立
   事实来源。
2. **Green（绿）**——只实现足以让该测试通过的行为，不要提前实现后续切片。
3. **Verify（验证）**——通过项目既有任务重新运行聚焦测试和最小相关回归测试集。

不要先规划全部测试、再规划全部实现。每次只针对一个行为重复 Red → Green。重构放在显式的 Green 后审查检查点：
在不改变行为的前提下改善结构，然后重新运行相关测试集。当公共接缝或轻量测试替身（fake）足以证明行为时，
不要模拟（mock）内部协作者。

## 计划格式

使用带复选框、以指令为主的步骤。默认采用以下紧凑结构；较小改动可以适当精简：

```markdown
# <功能>实施计划

## 目标与来源
- 源规格：<引用>
- 最终状态：<可观察结果>
- 范围外：<需要保留的边界>

## 仓库证据
- <当前行为、相关模块、既有测试惯例、适用 ADR>

## 实施策略
- 推荐路线：<路线及理由>
- 备选路线：<路线及未选择的理由>

## 已确认的测试接缝
- <公共接缝>：<它证明的行为>

## 依赖顺序
<简短有序列表或依赖图>

## 实施步骤
- [ ] 1. <祈使句、以结果为导向的 Tracer Bullet>
  - 交付：<可独立观察的行为>
  - 阻塞于：<步骤编号或“无”>
  - 涉及位置：<已核实的路径、符号、契约和生成边界>
  - Red：<第一个失败的行为测试、预期失败、命令>
  - Green：<最小实现指令>
  - 验证：<聚焦测试与回归命令>
  - 验收：<可证伪结果>

## Green 后审查与重构
- [ ] <不改变行为的结构审查/重构及重跑命令>

## 最终验证
- [ ] <项目验证任务与端到端证据>

## 未决事项
- <仅列出仍需人工决定的事项>
```

仓库证据充分时，使用准确路径和符号，但不要包含实现代码。明确区分制定计划时已经运行的命令和实施者之后必须
运行的命令。

## 交付前审计

- 源规格中的每项规范性需求至少由一个切片覆盖，且每个切片都能追溯到源规格。
- 不得凭空增加阈值、策略、兼容工作或产品行为。
- 每项验收标准都可被证伪；缺少对应行为时，它必须失败。
- 每个步骤都能独立以绿色状态落地，不存在隐藏的前向依赖或依赖环。
- Red 步骤应因目标行为缺失而失败，不能因为测试夹具损坏或与切片无关的编译问题而失败。
- 验证命令确实存在于当前仓库，并包含所有适用的项目门禁。
- 最终产物可由全新会话直接执行，不依赖未记录的对话上下文。
