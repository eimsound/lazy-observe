# 将 Issue AI 作为独立的持久分析任务运行

Issue AI 是核心可观测性预生产质量之后的可选功能，不属于错误摄取、Issue 生命周期或告警分发的完成条件。自动分析消费持久 `new_issue` 生命周期事实，手工分析消费经过授权的用户意图；两者都只创建或复用持久 Issue AI 分析任务，并在任务接管后通过异步 HTTP 契约返回，绝不在触发请求内直接调用模型。

数据库拥有权威任务状态、固定上下文快照、尝试和发布结果；主服务中的 Issue AI 协调器拥有资格、领取、租约、重试、取消和结算。请求 Worker 只通过同步且不感知任务的单次调用接口执行一个已经固定的 Provider 请求。缓存租约只协调执行活性，每次数据库接管推进单调 `claim_epoch`，所有发布与终态写入都以当前纪元为条件，因此租约丢失、缓存重启或迟到响应不能发布陈旧结果。

一个 Issue 最多存在一个活动任务，重复自动触发与手工请求合并到该任务；终态刷新创建新运行，只有成功的新运行替换最近发布结果。每个真实模型请求都对应一个预先持久化的尝试并消耗任务自己的预算，结构化输出修复也不例外。任务预算、上下文截止点和上下文字节上限在任务创建时固定；共享连接设置及 Issue AI 调用策略在每次尝试开始时读取一次并在该请求内固定。

上下文是同项目、固定截止点内的确定性有界快照。裁剪只控制相关性和体积，不承担隐私过滤；已经由客户端采集并进入平台的数据在被选中后原样发送给 Provider。可信指令与不可信遥测数据必须结构化隔离，输出必须经过严格契约校验。完整上下文、应用层调用、公开响应、用量和实际 Provider 配置在保留期内对项目可读用户可审计，但凭据、传输认证、缓存所有者令牌和 Provider 未公开内部信息永不进入产品记录。

## 已考虑的方案

- **进程内队列并同步手工调用（拒绝）**：实现简单，但进程退出、队满和请求超时会丢失意图，也无法阻止迟到结果覆盖当前状态。
- **复用错误 Inbox（拒绝）**：错误 Inbox 的 `2xx` 接管、20 次处理预算和 payload 清理属于遥测正确性；模型调用有独立成本、权限、上下文、取消和历史语义。复用表或预算会让可选 AI 反向成为核心错误处理的一部分。
- **持久任务加缓存租约和数据库纪元（采用）**：数据库提供最终正确性与恢复，缓存提供有界活性协调；代价是增加任务状态机、故障注入、结算背压和双方言持久化测试。

## 后果

Issue AI 可以在核心预生产功能之后独立排期、实现和验收。它依赖持久 Issue 生命周期事实和稳定错误身份，但不会反向阻塞这些能力。初始交付只覆盖单进程 All-in-One；Standalone 工作进程拆分、多副本共享租约和集群容量语义需在扩大部署范围前另行决策。

详细产品策略见 [Issue AI 持久分析规格](../specs/issue-ai-analysis.md)，实施顺序见 [Issue AI 持久分析计划](../plans/issue-ai-analysis.md)。
